KPI calculation journey

This is the easiest way to understand the dashboard flow. First the system reads raw files, then it cleans them, then it merges them, and finally it shows one KPI card to the user.

1

Raw business files are uploaded

Excel and CSV files from Amazon and Flipkart are uploaded exactly as business teams receive them.

Sales Spend Inventory
2

Upload parsers clean the data

The upload layer reads the needed columns, converts numbers, standardizes dates, and saves each raw source into database tables.

apps/upload/amazon.py apps/upload/flipkart.py
3

Processed daily rows are built

Sales, spend, category, and price are merged into one daily row per product so dashboard queries become much faster.

apps/upload/dashboard_builders.py apps/dashboard/services/daily_summary.py
4

Final KPI cards are calculated

The KPI service sums revenue, spend, units, page views, and growth for the chosen filters and time period.

apps/dashboard/services/metrics.py apps/dashboard/services/analytics_services_orm_pipeline.py

Worked example with simple sample data

These examples are intentionally simple. They are not real business results. They are here so a non-technical user can understand how one final KPI card is built from multiple files.

Example input: Amazon

From the Amazon daily sales file and Amazon spend file:

Revenue = 10,000
Orders = 120
Units = 150
Page Views = 3,000
Ad Spend = 2,000

Example input: Flipkart

From the Flipkart search traffic file and PLA file:

Revenue = 6,000
Units = 40
Product Clicks = 2,000
Ad Spend = 1,000
Product Status = Continued

Example result: Combined KPI

What the dashboard can show after both sources are merged:

Total Revenue = 10,000 + 6,000 = 16,000
Orders = 120 + 0 = 120
Units Sold = 150 + 40 = 190
Traffic = 3,000 + 2,000 = 5,000
Ad Spend = 2,000 + 1,000 = 3,000

Example for ROAS, TACOS, and DOC

The current code adjusts revenue by 70% before ROAS and TACOS. Inventory DOC is calculated with stock and daily run rate.

Adjusted Revenue = 16,000 x 0.7 = 11,200
ROAS = 11,200 / 3,000 = 3.73x
TACOS = 3,000 / 11,200 x 100 = 26.8%

If stock = 300 units and average daily run rate = 10 units,
DOC = 300 / 10 = 30 days

Business cautions before using the numbers

These points matter because a KPI can be technically correct according to code but still be misunderstood by a business reader.

1. Flipkart orders are not fully loaded into the Orders KPI

The current pipeline maps Flipkart traffic Sales to units, not orders. So the Orders card is mostly Amazon-backed today.

2. ROAS and TACOS use 70% of revenue

The current formula uses Revenue x 0.7 before ROAS and TACOS. This is an intentional business rule in the code.

3. Flipkart clicks are treated like page views

The raw Flipkart search traffic file gives Product Clicks, and the KPI logic uses that as traffic / page views.

4. Growth KPIs need history

MOM and YOY only make sense when previous periods are already loaded. If history is missing, those percentages can mislead users.

5. Inventory KPIs need date alignment

Stock and sales must belong to the same reporting dates. If inventory is from one date and sales are from another, DOC and stock health can look wrong.

6. Amazon inventory health needs matching stock files

The backend can calculate Amazon inventory health, but only if the right Amazon stock files are uploaded for the same dates as sales.

If a business user asks "why is this KPI different from my Excel?"

  • First check whether the dashboard is mixing Amazon and Flipkart together.
  • Then confirm which raw files were uploaded for that date range.
  • Then verify whether the KPI uses gross revenue or adjusted revenue.
  • Finally check whether the metric is using orders, units, clicks, or page views, because these are not the same thing.
